## Codex lane 401 `sk-svcacct` incident — upstream, not local

A Sol-main session in another project failed twice with `503 auth_unavailable … providers=codex, model=gpt-6-sol; last upstream error: auth_unavailable: Incorrect API key`, including once after a bare `continue`. Global rule 4 applied: the fan-out stopped, nothing was retried, no lane was switched, and no reset or re-login ran.

**Observed facts** (read-only; pinned local proxy build, running since 2026-09-22):

- Exactly four `Incorrect API key` errors in the whole proxy log, all within `18:38:39`–`18:43:15`. None before, none since; `gpt-6-sol` traffic resumed with 200s by `21:50`.
- Every credential on the lane failed, so failover had nowhere to go, and `gpt-6-astra` failed the same way. The lane was down, not one model.
- The rejected credential was reported as `sk-svcacct-…` — identical across distinct credentials whose own tokens differ.
- That value exists nowhere local: not in `config.yaml` (whose keys are the client key and the OpenRouter key), not in the proxy process environment, not in shell profiles or repo snippets, not in any running process.
- Each 401 was preceded within about a second by `auth file changed (WRITE)` on the exact credential in use — four auth-file writes in five minutes.
- The error cited the platform API key page, not the ChatGPT backend that Codex OAuth actually uses.

**Corrected diagnosis.** The first reading — that the proxy's incremental auth-file reload raced an in-flight request and substituted a shared fallback key — was wrong, and was stated to the human with more confidence than the evidence carried. The identical value across distinct credentials was treated as proof of a local shared fallback; it is equally explained, and better explained, by the key not being ours at all. `sk-svcacct-…` is OpenAI's own backend service-account credential echoed verbatim in the error body. Independent reporters hit the identical signature on 2026-09-25 with **no proxy**, on hosts reporting `stored API key: false` and `stored auth mode: chatgpt`, through a third-party agent, and across several models. The fault is inside `chatgpt.com/backend-api/codex/responses`, where the caller's OAuth identity is not the credential being validated. Upstream `openai/codex` [#48237](https://github.com/openai/codex/issues/48237) is open with no maintainer response; [#48265](https://github.com/openai/codex/issues/48265) closed as its duplicate. Same-signature reports: [#48256](https://github.com/openai/codex/issues/48256), [#48259](https://github.com/openai/codex/issues/48259), [#48260](https://github.com/openai/codex/issues/48260), [#48287](https://github.com/openai/codex/issues/48287), [#48300](https://github.com/openai/codex/issues/48300), [#48306](https://github.com/openai/codex/issues/48306).

**Method lesson.** A correlation in the logs (`WRITE` then 401) was promoted to causation before checking whether the offending value could originate locally. The disconfirming check was cheap — the key was absent from every local source — and should have preceded the causal claim rather than following it. Timestamp adjacency between a local event and a remote failure is not evidence of local origin.

**Open follow-up, worth a guard.** Four auth-file writes in five minutes matches the refresh-storm pattern in [#48303](https://github.com/openai/codex/issues/48303): a 401 that is not about the caller's credential is treated as recoverable, so every retry runs reload → refresh → retry. One reporter logged 36 refreshes in six minutes. ChatGPT refresh tokens are single-use, so this can burn or concurrently rotate them. The defensible local change is to skip auth recovery when a 401 names a credential that is not ours — not the reload race that was originally hypothesized. Not implemented; no proxy code, config, credential, or cooldown state was touched.

**Also confirmed by exclusion.** This was never a quota cooldown, so `cliproxy-reset-quota` would have been the wrong tool; re-login would have done nothing, since the credentials were valid and freshly refreshed; and a proxy restart was declined because several other sessions were mid-flight on it.
