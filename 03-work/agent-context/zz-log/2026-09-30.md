## Computer-use sandboxing research

- **Question:** can an agent drive a GUI while the owner keeps using the machine, without having to focus windows?
- **Method:** three Sonnet research workers (sandbox stacks, integration and safety, no-focus input). Research only; no files changed.
- **Findings:**
  - A sandboxed display removes the focus problem entirely. cua is ranked first, then a libvirt VM with a community MCP server, then Webtop with computer-use-linux in the guest.
  - Focus-free control of the real Wayland desktop is limited to AT-SPI actions and the browser via CDP.
- **Crumb:** `zz-research/2026-09-30-computer-use-sandboxing.md`. The next step is a hands-on cua trial to settle the Podman, RAM and Claude Code MCP questions.
- **CLIProxyAPI fit:** the owner asked whether this works with CLIProxyAPI. It does: MCP tools run locally in Claude Code, and the proxy only carries model traffic. Two constraints follow:
  - Never enable a sandbox product's own agent loop, since it would bypass the proxy, the meters and the guard.
  - Whether tool-result screenshots survive the translation to GPT lanes is unverified.
- **Plan:** `02-stack/01-ai-coding/sandboxed-computer-use-plan.md` (`status: planning`) holds the architecture, ranked stacks, safety defaults and a 9-step trial with pass gates. The trial includes a Claude-lane vs Sol-lane image-passthrough test and an accessibility-only fallback. It is indexed in `01-ai-coding/index.md`.
- **Trial ran (steps 1–8):** a Sol worker did the local steps 1–4, then the orchestrator ran steps 5–6 with owner approval.
  - The cua desktop runs under rootless Podman: ~0.9 GB idle, a 12.2 GB image, loopback-only ports, egress blocked, a read-only share, and a clean reset.
  - Legacy `cua-mcp-server` is ruled out because its agent-loop tools always register. The narrowed in-image `computer_server` MCP (5 tools, no model key) works from headless `claude -p` via `--mcp-config --strict-mcp-config`.
  - **Screenshots survive CLIProxyAPI to GPT-6.1 Sol.** Both Sonnet 5.5 and Sol read a random on-screen code and typed its reverse correctly.
  - Remaining gaps:
    - The KasmVNC viewer clipboard is on by default.
    - The guest accessibility tree is empty.
    - Guest sessions need their own permission kind, a proposal for the permission-core owner.
  - The plan doc was promoted to `status: research` with a results table.
- **Clipboard fixed (same day, after PR #27):** a Sol worker found why the runtime flags failed.
  - `vncserver` only recognizes spaced options (`-SendCutText 0`), not `=` forms.
  - It then appends the YAML defaults, which enable clipboard. `KASM_SVC_*` is a second, unset override point.
  - The fix is a small, offline-built derived image with clipboard-off system YAML, spaced flags in both env hooks, and a narrowed runtime-override allowlist.
  - Verified six ways, including a headless RFB probe with a positive control. The plan doc gained a "Clipboard fix" section and the open question is closed.
  - The guest-session permission kind is now the only blocker to routine use.
