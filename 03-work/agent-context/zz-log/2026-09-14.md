## Desktop computer use: workspace binding, first field run, and the isolated-display lane

- Earlier today, before the field run: workspace binding enforcement landed — `b1949d2`, `eligibleHandle` in `profiles/desktop-bridge/lib/session.mjs`, 6 tests, suite 179. Bridge reinstalled afterwards. User-scope registration confirmed for all workspaces (`40e0bc5`).
- The "6 earlier requests expired undecided" the controller showed were stale Sept 6–8 browser and model requests, not churn from today.
- **First real governed run, in an Electron-app project (shared-seat lane).** One screenshot succeeded end to end. Everything around it went badly enough to be worth the detail:
  - The agent first filed a request guessing the app's short name as `appId`. The real `app_id` is `com.vendor.app`. Matching is exact, case-sensitive, and on `app_id` only (`lib/scope.mjs:100`); `wm_class` is extracted by `lib/window-facts.mjs` and then never used. Corrected request approved.
  - `stop-desktop-bridge` killed the child but left the proxy alive **and the grant active** — `lib/stop-session.mjs` never releases the grant in the core.
  - The proxy resolves its grant **only at startup** (`lib/session.mjs` / `lib/proxy.mjs`), so a later approval was never picked up, and `/mcp` reconnect did not respawn the process.
  - The `PreToolUse` guard (`hooks/desktop-mcp-guard.py`, deny branch ~L252-260) then said "no `desktop_session` grant was approved" while an approved handle was sitting right there. The agent chased that message in circles. Recovery was a fresh `claude` process.
  - Two human-factor refusals: the agent refused an in-scope click by reading the `purpose` sentence as a restriction, and a screenshot was refused because the human had the terminal focused — captures are focused-window-only by shared-seat design.
- Five-bullet fix list agreed and **in progress** (separate worker, today): lazy grant pickup plus `notifications/tools/list_changed`; stop releases the grant and returns the proxy to waiting; honest guard message when a handle is waiting; `appId` matches `app_id` **or** `wm_class` case-insensitively and `focused_window` becomes a default op with a documented bootstrap; instructions state that `purpose` is descriptive not restrictive, and the default envelope goes to 30 min.
- **"Mask the other windows" was ruled out, not deferred.** The vendor binary captures through the portal and injects through `uinput`, both on the real seat. A masking capture proxy leaves input untouched (focus stealing, keystrokes into the human's window) and cannot be enforced against the binary at all. The model everyone else actually uses is a separate display, not a VM.
- **Isolated-display lane spike (lane 2), verified:** a private Xvfb display started as this user is genuinely capture-isolated — a screenshot of `:97` showed only what was launched on `:97`; display killed and verified gone afterwards. Also verified: the vendor binary **ignores `DISPLAY`** — pointed at the private display it still captured the real desktop and still injected to the real seat. So the vendor binary cannot be lane 2's child.
- **Forced-X11 re-test refines the "ignores `DISPLAY`" finding without reversing it** (read-only, `doctor` only — no screenshot or input tool was ever called). Under `env -i PATH HOME USER LANG DISPLAY=:97 XDG_SESSION_TYPE=x11 XDG_RUNTIME_DIR=<scratch>`, no `WAYLAND_DISPLAY`, no `DBUS_SESSION_BUS_ADDRESS`: input `["abs_pointer","xdotool"]`, screenshot `["portal"]`, window_control `["kwin"]`, isolation `["shared"]`. `DISPLAY` is honoured for the **xdotool keyboard path only**. Complete force-knob set is `FORCE_XDOTOOL_KEYBOARD`, `FORCE_YDOTOOL_KEYBOARD`, `FORCE_YDOTOOL_POINTER`, `FORCE_PORTAL_POINTER`, `FORCE_PORTAL_KEYBOARD`, `SCREENSHOT_BACKEND` — no XTEST pointer force, and no X11 capture backend in the binary at all (no `import`/`scrot`/`xwd`/`maim` strings; only portal and `gnome-screenshot`). `SCREENSHOT_BACKEND` tried with `x11`/`import`/`xdotool`/`auto`/`portal`/garbage: always `["portal"]`, invalid token silently accepted. The X11 window backend needs `wmctrl` (not installed) and loses to KWin whenever the session bus is reachable. Two of three needs are missing upstream features, not config — v0.5.0 stays disqualified as the lane-2 child.
- **Env scrubbing is not containment.** With `WAYLAND_DISPLAY` and `DBUS_SESSION_BUS_ADDRESS` unset, `doctor` still found `unix:path=/run/user/<uid>/bus`, the real `XAUTHORITY`, `xdg_current_desktop: KDE`, all five portals answering ok, and `/dev/uinput` read/write. sd-bus derives the bus path from the uid; only a uid/namespace/socket boundary would sever it. Written into the research note's hazard callout as a second point.
- **Search resolved, decision taken: write `x11-child`** (Node, zero deps, `xdotool`/`import`/`xprop`). No maintained X11-native computer-use MCP server exists worth vendor-pinning; the only runner-up, `tak-uukti/linux-computer-use` (Python + AT-SPI, `xdotool`/`scrot`, no shell tool, ~3 stars), would add a Python dependency chain and is kept only as a named fallback. Install state: `xdotool`, Xephyr, `import`, `xprop` already present; only `openbox` may be missing; `wmctrl` and `scrot` absent and not needed.
- Design rewritten around a second, bridge-owned `x11-child` MCP server over `xdotool` (XTEST), `import`/`xwd`, and `xprop`, bound to the private display. New `terms.display` and `terms.launch` (argv printed verbatim on the card); launcher asserts `DISPLAY=:N`, `QT_QPA_PLATFORM=xcb`, `GDK_BACKEND=x11`, `ELECTRON_OZONE_PLATFORM_HINT=x11`, `WAYLAND_DISPLAY` unset. `O_EXCL` lock files, display numbers ≥ `:90` (`:99` belongs to another project's harness). Per-mode attestation inverts: lane 1's required `uinput` marker is a **failure** marker in lane 2. Viewer is Xephyr (local X client, no listening socket); `x11vnc` only on request, bound to `127.0.0.1`.
- Two of the user's own Obsidian-plugin projects already gate on private-Xvfb runs (`linux-x64-xvfb` attestation, env allowlist, display-failure regex), so the lane is consistent with existing practice.
- Human decisions: install `xdotool xorg-x11-server-Xephyr openbox` (human runs `dnf`); **residual risk accepted** — the private display runs as the same user on the same filesystem, so the boundary is display/input isolation, not a sandbox; "invisible or visible both fine"; a viewer is wanted.
- Effort estimate: 7 bounded chunks, ~1,900 lines, ~60–65% reuse of the existing bridge.

## OpenRouter lane: GLM 5.3 Flash as a fourth, prepaid meter

- **Why:** both subscription pools were running dry. A metered API fallback was wanted with a **$20 hard cap**, one model only (`z-ai/glm-5.3-flash`), selectable from the `ccx` launcher family. Route A (through CLIProxyAPI's `openai-compatibility` provider, alias `glm-flash`) was chosen over OpenRouter's Anthropic-format skin because it keeps the single allowed proxy origin and needs no second guard route; the one open question — whether the proxy translates Anthropic-format inbound to an OpenAI-compatible backend — was answered by the smoke test, not the docs.
- **Cap lives on OpenRouter, not here.** The per-key credit limit ($20, reset never) is the only dollar-aware stop; the guard only learned a pool label. When the key is spent the route 402s and the rule is stop, not retry. Nothing on this machine counts dollars.
- **Key UX:** `profiles/cliproxy-openrouter/` — `openrouter-set-key` (kdialog password box, `getpass` fallback; writes only the `openrouter` item of the `openai-compatibility:` block into the proxy config, atomic 0600, backup kept, fingerprint-only output, `--force` / `--remove` / `--allow-any`) and `openrouter-smoke` (one text ping plus one tool-call request through `127.0.0.1:8317`, cost estimate). The model list is a key-less repo manifest; re-running set-key refreshes models and leaves the stored key alone. Installer with `--check` digests; 33 tests, no key literal anywhere. The `:free` variant of the model does not exist — a worker asserted it did, the live model list said otherwise.
- **Guard and launchers:** `glm-flash` added to every closed enum (`WORKER_MODEL_POOLS`, `DISPATCH_POOLS`, `SUPPORTED_WORKER_MODELS`, `ROUTE_MODELS["local-proxy"]` only; policy `modelPools` / `directAgentApproval`), pool label "prepaid OpenRouter credit", never premium. `CANONICAL_DISPATCH_SHA256` recomputed `6662183f…` → `0c30980c…` and re-pinned in the policy JSON; the installer holds an independent literal copy of the direct-agent map and had to change too. `cliproxy-auth-check.py` sees the provider through `GET /v0/management/openai-compatibility` (never the config file); new state `provider-unconfigured`, exit 15, deliberately not `login-required` so the launcher can never offer a login that does not exist; `--reset-quota` refuses `openrouter` because a spent prepaid key is not a proxy cooldown. `glm-worker` added to `opusxm` / `claudexm` / `astraxm` / `fablexm`; new `glmxm` lane (GLM main, flexible, `glm` / `sonnet` / `sol` / `opus` workers) with a `ccx` menu row and launcher-matrix row.
- **Review catch:** the first cut of `glmxm` hard-required both OAuth providers before launching — which refuses exactly the situation the lane exists for. Now: proxy up → OpenRouter **hard** gate (`glmxm: openrouter provider not configured — run: openrouter-set-key`) → Claude/Codex health as **warnings only** → launch. Negative test: `glm-flash` on `native-anthropic` is denied.
- **Field run (human-executed):** install → `openrouter-set-key` → proxy restart → smoke. Two gotchas: `cliproxy-restart` was not in the shell (helpers sourced before the function existed; re-source fixes it) and its y/n prompt reads "no" under the `!` runner, so `systemctl --user restart cliproxyapi-managed.service` was used. Smoke: text OK, but the tool request returned `stop_reason: max_tokens` at the 32-token default — GLM is a reasoning model and spends the budget thinking. At 512 tokens: `stop_reason: tool_use`, tool block present. **Route A proven for text and tools, $0.00013 total.** Smoke default raised to 512.
- **Third gotcha — the silent non-launch.** First `x` → glmxm from `~/MEDIA` printed the Sol→GLM migration notice and the `→ glmxm --fork-session -r …` line, then dropped back to the prompt with nothing launched. Cause: `ccx` records launcher state *before* exec, and `_cc_launcher_state_known_brain` (helpers) is a closed brain list that did not include `glmxm`, so `_cc_launcher_state_write` returned 1 and `ccx` did `|| return 1` with no message. Three closed lists needed the brain (`known_brain`, `cross_provider_brain`, and `cc-handoff`'s case), and the `ccx` failure path now prints `ccx: refusing to launch: could not record launcher state …` instead of exiting mute. Regression test `test_glmxm_is_a_known_launcher_state_brain`. Lesson for the next lane: adding a brain touches the launcher-state enum too — the launcher tests pin the exact case string, which is how the test caught nothing (the pinned string was copied, not derived). The migration notice itself is expected: the newest session in that directory was a Sol session, so `ccx` forks its history under GLM; pick `fresh` in the session picker to avoid it.
- **Cost picture** captured in [`zz-research/2026-09-14-cost-effective-coding-models.md`](../zz-research/2026-09-14-cost-effective-coding-models.md): GLM 5.3 Flash at ~$0.50/M out is ~20× cheaper than Sonnet or Sol-via-OpenRouter and ~100× cheaper than Fable/Astra; Sol's value is the subscription pool, not its API price. $20 ≈ 40M output tokens.
- **Follow-ups, not done:** a `glm-settings.json` compaction profile (Claude Code assumes 200k for unknown model IDs; GLM's window is larger); `03-work/rebuild/03-shell-helpers.md` and `04-ai-tools.md` do not list `glmxm`; the four existing `*xm` lanes offer `glm-worker` without preflighting OpenRouter, so selecting it there fails at request time rather than launch; the installed `openrouter-set-key` reads the manifest from the repo path, so moving the repo needs a re-install.
