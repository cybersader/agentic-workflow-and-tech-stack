## WSL crash attributed: bundled search consumed 16.5 GiB

- The mem-watchdog added on July 20 produced the first decisive pre-crash receipt. From at least 13:30 until WSL shutdown at 13:52, one Claude Code search worker had **16,552–16,563 MiB RSS**. Its process `comm` appeared as the bundled version (`2.1.215`), while argv began `ugrep -G --ignore-files --hidden -I ...`; this was Claude Code's bundled search, **not ck** (the ck quarantine held).
- Consequence was observable rather than inferred: WSL's 2 GiB swap remained **100% full**, memory PSI `some` stayed approximately **92–99%**, and MemAvailable hovered near 3 GiB while five Claude sessions and an Astro process shared the remainder. WSL then entered a systemd shutdown at 13:52; the journal shows orderly service termination followed by WSL's forced power-off fallback, not a Linux OOM-killer event.
- Disk space was not the trigger: C: still had approximately **54–55 GiB free** throughout the pressure window. The Downloads-to-NAS robocopy was also not the memory consumer; it had independently wedged on SMB `ERROR 121` after reaching 94 files / 5.22 GiB.
- This evidence narrows the earlier generic July 20 theory. The 24 GiB WSL cap leaves too little host reserve under load, but this specific recurrence had a named in-VM cause: an unbounded search worker consumed roughly two-thirds of the VM by itself.

## Deterministic search-runaway rail

- Extended `profiles/watchdog/mem-watchdog.sh` with `MEMWATCH_SEARCH_KILL_MB` (default **4096 MiB**, `0` disables). Every 30-second sample now inspects argv and terminates an `rg` or `ugrep` worker above the threshold: TERM, one-second grace, then KILL. Matching argv is deliberate because the runaway's `comm` was `2.1.215`, not `ugrep`.
- The action logs its own `!! ... killing runaway search` forensic line before termination. Search workers are deliberately treated as expendable; the threshold is high enough for large legitimate scans while stopping the exact failure class before it can consume the VM.
- Validated with a synthetic process whose argv[0] was `ugrep`: at a 1 MiB test threshold, the watchdog detected and killed it and emitted the expected receipt. The current post-reboot broad `rg` scan over `Documents/4 VAULTS` was manually stopped at approximately 500 MiB as an immediate precaution.
- Fixed two deployment defects discovered while activating the rail: `mem-watchdog.service` had invalid `CPUQuota=5%%` (corrected to `5%`), and `install-watchdog.sh` used `enable --now`, which did not replace an already-running process after script updates. The installer now enables then explicitly restarts the service.
- Reinstalled and verified live at 14:03: new watchdog PID, 64 MiB MemoryMax, effective 5% CPU quota, installed kill-rail code, approximately 21 GiB available memory, 0% swap, and 0% PSI.

## SMB offload paused after crash

- Downloads banked on the NAS: 94 files / 5.22 GiB out of a local 17,177 files / 63.75 GiB. The Windows robocopy process remained stuck on an SMB semaphore timeout; normal Stop-Process/taskkill could not terminate the stale process and CIM termination returned access denied. No supervisor was relaunched after the WSL restart.
- Keep the offload paused while stability is verified. Resume later under the bounded `robocopy-supervisor.sh`; perform authoritative verification before deleting any local Downloads content.

## Workflow agent-cap bypass attributed and contained

- A separate Velociportal session demonstrated that the July 17 `agent-guard` was not a real Workflow hard cap. Two outer Workflow calls materialized 111 nested agent transcripts (8 project-init + 103 bundled deep-research). No cap override or raised environment value was active.
- Root cause: the PreToolUse hook counted agent transcript files already present when the outer call began. Workflow-internal `agent()` calls do not re-enter the parent's blocking Agent/Workflow PreToolUse boundary, transcript receipts lag execution, and concurrent/background calls can pass the same preflight count. The completed session is blocked retrospectively at 111, but that cannot stop an in-flight workflow.
- The bundled deep-research workflow's shape was the multiplier: up to 25 claims × 3 verifier agents = 75 verifier calls, plus scope/search/fetch/synthesis. Its relevance-dependent fetch filter was not a true cap, and the observed run reached 103 agents by itself.

## Atomic admission guard + bounded deep-research installed

- Replaced transcript-only preflight with a two-layer control under `profiles/claude-global/`: Python-standard-library admission logic behind the stable `agent-guard.sh` hook, an explicit JSON policy, and an idempotent installer.
- Defaults are now consistent: **15 agents per genuine user prompt** and **40 per rolling 5h session**. Direct Agent calls reserve one unit. Named, inline, resumed, unknown, path-changed, and hash-changed Workflows fail closed. Only an exact manifest-registered `scriptPath` can reserve its complete declared maximum.
- Reservations are append-only JSONL under an exclusive `flock`; concurrent hook processes cannot observe and spend the same remaining budget. Materialized transcript counts remain reconciliation evidence, with usage computed conservatively so receipts and reservations are not double-counted.
- Removed the agent-writable `agent-cap-off` mechanism. Numeric overrides are accepted only from the launch environment (`CLAUDE_AGENT_CAP`, `CLAUDE_AGENT_SESSION_CAP`) and cannot weaken the Workflow trust policy. The obsolete empty sentinel discovered during installation was inspected and removed.
- Added a personal `deep-research` skill override with a hash-registered workflow and a literal 15-agent scheduler: 1 scope + 4 search + 4 bounded fetch/extract + 5 batched adversarial verifiers + 1 synthesis. Every call passes through one budget wrapper; no schema retry path or replacement-agent path exists. The bundled named workflow is independently denied.
- Verification: 14 guard unit/race tests, mocked Workflow tests, and installer idempotency/rollback tests all pass. A 20-process admission race allowed exactly five calls against a five-agent cap. Nested-session and policy-hash regressions prove child session IDs consume the normalized root budget and policy edits fail closed until reinstall. Installed-hook smoke tests denied named/inline/unknown Workflows, admitted the registered 15-agent script, then denied an extra same-prompt Agent—all without launching real agents.
- Published the sanitized upstream report as [anthropics/claude-code#79953](https://github.com/anthropics/claude-code/issues/79953) after explicit human approval. Final checks found no personal/project identifiers, no matching existing issue, and current documentation still describes `SubagentStart` as non-blocking. The report uses only a synthetic five-agent example and generic paths; the observed environment remains accurately identified as Claude Code 2.1.216 (the filing client was 2.1.217).
