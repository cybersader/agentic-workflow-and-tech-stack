## Agent-guard: raised default cap, generalized registration, renamed harness

- Raised default `sessionAgents` **40 → 80**. Root cause of repeated hits: the guard reserves each workflow's full declared max for the entire rolling 5h window and never auto-releases even after completion, so a few big approved workflows (e.g. 15+11+7) fill 40 fast. Justified now that all fan-out is bounded/approved (the unbounded runaway that set 40 can't recur). Prompt cap stays 15. Synced both CLAUDE.md copies + the installer's summary (which was printing a hardcoded "40").
- Found and fixed a regression I introduced: the approve-workflow installer hardcoded `deep-research` as the ONLY registered workflow, so it silently de-registered `cleanyfin-parallel` — that's why recent workflows showed `request=approved-scriptPath` (approved each time) instead of running registered. Generalized `install-agent-budget.sh` to install + hash-register **every** entry in `policy.approvedWorkflows` (validates each: id/maxAgents/source-exists, and that the declared bound `maxAgents:`/`MAX_AGENTS=`/`HARD_CAP=` equals the registered maxAgents). The guard already matched multiple manifest entries, so no guard.py change.
- Renamed `cleanyfin-parallel` → **`bounded-parallel`** (the old name was project-specific/misleading for a general harness). Created the canonical at `profiles/claude-global/workflows/bounded-parallel.wf.js` (identical logic, HARD_CAP=6), added it to the policy, registered it (max 6), removed the old `~/.claude/workflows/cleanyfin-parallel.wf.js`. The surfaced skill renamed automatically (it's the workflow `meta`). Verified live: `bounded-parallel` is admitted with zero approval.
- Added a **`register-workflow <path.wf.js> [maxAgents]`** helper: copies a reusable workflow into the repo canonical, adds a policy entry, and reinstalls — so future reusable workflows become permanently registered (no approvals) and rebuild-safe. Only genuinely one-off scratch workflows now hit the approval gate.
- Design clarification recorded for the user: approval gates on **admissibility** (is this un-registered/opaque workflow trusted to run), NOT on budget. It can't gate on budget because the budget number is unenforceable for un-registered workflows (internal `agent()` calls bypass the hook — upstream #79953). Registered workflows are trusted (hash-pinned, self-enforcing) so they need no approval; the friction fix is registration, not budget-gating.
- Verification: 21 guard tests + 2 installer tests (now asserting both registered workflows) + deep-research mocked tests all pass. Installer redeployed; manifest shows deep-research (15) + bounded-parallel (6); live smoke test confirmed bounded-parallel admitted without approval.

## C: recurrence (structural): non-sparse VHDX growth + pagefile

- C: hit ~14 GiB free again. This time crash dumps were minor (1.9 GiB, deleted). The real consumers: the Ubuntu `ext4.vhdx` grew to 108 GiB host (guest usage 71→87 GiB this session) and the Windows pagefile sits at 26 GiB allocated (peak 7 GiB). Because the VHDX is non-sparse, freeing guest space does NOT return C: space without an offline compaction.
- Structural conclusion: in-guest cleanup (`disk-slim`) cannot fix C: on its own; durable reclaim needs a one-time offline maintenance window (`wsl --shutdown` → compact the VHDX → applies `maxCrashDumpCount=0` → optionally cap the pagefile → reduce WSL memory 24→18 GiB so Windows keeps headroom). Steps need a real Windows terminal / admin and kill running WSL sessions. See `profiles/watchdog/BREAK-CHECKLIST.md`.

## One-shot human approve-workflow escape hatch

- Motivation: a bundled named workflow (`knowledge-capture`) was correctly denied by the guard; the only exits were "use direct Agents" or permanent registration. Added a human-in-the-loop middle path.
- Mechanism (append-only, fail-closed): a blocked-but-approvable Workflow (unregistered `scriptPath`, or a named workflow) records an `approval-request` with a short nonce and prints a card. A **human** types `approve-workflow <nonce> [agents=N]` as a normal message; a new `UserPromptSubmit` hook (the guard's `approve` subcommand) writes a one-use, TTL-bounded (10m), session-bound, hash-pinned `approval-grant`. The next matching Workflow call consumes it and reserves the approved agent count against the normal budget. Named workflows require an explicit `agents=N` (opaque internal fan-out is a trust ceiling, not enforcement); scriptPath grants are pinned to the file hash so an edit after approval voids them.
- Threat model (documented honestly): the agent cannot emit a UserPromptSubmit, so it cannot self-approve in its normal flow, and every grant is auditable in the append-only ledger. This is human ergonomics + audit under the same non-adversarial model as the rest of the guard, not a defense against an agent deliberately writing state with shell access.
- Behavior change: named workflows shifted from hard-denied to denied-by-default-but-approvable-once. Two existing tests were updated to assert the card (still return 2) rather than the old "named Workflows" message; the numeric-override test still proves a raised cap alone never admits a named workflow.
- Wiring: `approvalTtlMinutes: 10` added to the policy; installer now merges + verifies the `UserPromptSubmit` approve hook alongside the `PreToolUse` guard; `agent-cap-status` and both CLAUDE.md copies document the escape hatch.
- Verification: 21 guard tests (14 original semantics preserved + 7 new), 2 installer tests, and the deep-research mocked tests all pass. Ran the installer against the real profile; installed guard/policy hashes match canonical; `status` shows the approval line; a live end-to-end run against the installed guard confirmed card → approve → admit → one-use-spent. The `model` setting was preserved through install.
