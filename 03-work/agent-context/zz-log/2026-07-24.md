## WSL crash-dump recurrence exhausted the host drive

- C: reached approximately **3 GiB free** while Linux itself remained healthy at approximately 20 GiB available memory, negligible swap use, and no memory PSI. This recurrence was host-storage pressure rather than a Linux memory runaway.
- `%LOCALAPPDATA%\Temp\wsl-crashes` contained the WSL default maximum of ten retained process dumps totaling **54.54 GiB**. Three browser-based Obsidian process crashes accounted for approximately 53.85 GiB individually: 16.70, 18.89, and 18.26 GiB. The remaining files were earlier terminal-process dumps.
- After explicit human approval, deleted exactly those ten `.dmp` files. Verification showed zero remaining dumps and C: recovered to **57.54 GiB free**. No workspace files were touched.
- Added `maxCrashDumpCount=0` under `[wsl2]` in the live `.wslconfig`. The installed WSL version is 2.7.10, which contains the zero-count crash-collection fix introduced in WSL 2.7.0. The setting will apply at the next natural WSL restart; no shutdown was forced during active work.

## Sol proxy authentication interruption was transient

- A proxied Sol session received repeated `503 auth_unavailable: no auth available` responses for the Codex provider. The proxy process and port remained healthy, and the model stayed present in the catalog.
- The proxy recorded rapid 503 responses from approximately 12:01 through 12:21 UTC. A later minimal authenticated request to the same model returned HTTP 200, so the lane recovered without credential replacement or a retry loop.
- Treat this error as a provider/auth-eligibility interruption rather than damage to the active workspace. Stop repeated retries, preserve the session, and probe the lane once after a short interval.
