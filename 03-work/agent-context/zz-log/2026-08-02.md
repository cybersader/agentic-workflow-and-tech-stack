## Portagenty finder: naming a directory you already know

- The reported symptom was "I can't attach a workspace to my user folder." The finder was tuned for *discovery* — fuzzy-ranking a walked corpus — and had no path for the case where the user already knows the answer. Typing a bare leaf name lost to hundreds of deeper matches; the only scope controls (`←`/`→`) re-rooted off the *highlighted row* rather than the current root, and every scope change silently cleared the query.
- Shipped `Ctrl+G` ("Go to path"), prefilled with the current root: Enter expands `~`/`${VAR}`, requires an existing absolute directory, and re-roots there; a bad path shows an inline error instead of re-rooting. Exact-path pinning now also accepts env-expanded paths, trailing slashes, and `.`/`..` segments — resolved lexically, never canonicalized on the TUI thread (DrvFs stat latency stalls rendering).
- `Ctrl+R` (global toggle) now **preserves** the typed query. Widening a search means "the same thing, somewhere bigger"; discarding the query there was the single most confusing behavior in the overlay.
- Footer and empty-state text now surface `Ctrl+G` and `Ctrl+R` and state that typing a full path jumps to it. None of it was discoverable before — the fix was half implementation, half telling the user it exists.

## A non-atomic config write, surfaced by the test suite

- Chasing test flakiness turned up a real product bug: every global-config mutation used a plain `fs::write`, which truncates then fills. A concurrent reader saw a partial TOML document and failed with `expected `.`, `=``. Running several `pa` processes at once is normal (picker in one pane, `pa launch` in another, agent session in a third), so this was reachable in ordinary use — it just looked like config corruption rather than a race.
- All six write sites now go through a `write_atomic` helper (temp file → fsync → `rename`), mirroring `state::save_to`. Regression test hammers the path from a writer loop while a reader thread parses continuously.

## Process-global env leakage between tests

- Rust runs a crate's unit tests as threads in one process, so `set_var` is process-global. Tests in `state`, `snippets`, and `config::merge` set `HOME=/home/test` and never restored it; whichever test ran next inherited it, and the onboarding wizard then failed with `Permission denied`. Failure identity and count changed run to run.
- The onboarding tests were the other half: they wrote their `.onboarded` sentinel into the **real** `$XDG_STATE_HOME`, as an existing comment conceded.
- Added a shared `test_env::EnvSandbox` — restores prior values on drop (including was-unset, and on panic) **and** serializes all env-mutating tests behind one process-wide lock. Restoring without serializing is insufficient: two guards still interleave. Converted the pre-existing `TempXdg`/`Sandbox` guards too; they restored correctly but did not serialize.
- Full suite went from 6/8 runs green to 10/10, then 335 + 48 + 6 + 10 passing.

## Receipts on the one-run dynamic Workflow path

First real use of the admission class added [[2026-08-01]]. Three findings worth keeping:

- **It worked as designed.** A 6-agent, 3-phase (audit → apply → verify) task-specific script was authored, blocked, approved once by exact human turn, and ran — without permanent registration. The Apply phase ran *sequentially* because all three agents edited one file; `bounded-parallel` could not have expressed it.
- **The model-escape detector produced a false positive.** It matched the literal `model:` inside a *comment* ("selects no worker model: …"). It scanned raw source, so any prose containing that token tripped it. Reworded the comment at the time rather than weakening the guard; **fixed properly later the same day** (see below).
- **The verifier agent was confidently wrong about provenance.** It labeled a failing test "pre-existing flakiness"; the test was *new, added by that same run*. Verified independently by stashing all work and running the baseline (311 passed / 3 failed) — which confirmed the onboarding failures were genuinely pre-existing while the finder ones were not. Adversarial verification still needs an independent baseline, not just a re-run.

## Static analysis must read code, not prose

- Fixed the detector properly: `strip_js_noise()` blanks comments and string contents before any escape or bound pattern runs. The false positive mattered beyond the nuisance — the natural workaround is to reword the comment, which leaves the real policy unexamined. A check that punishes vocabulary instead of behavior trains the wrong reflex.
- Template `${...}` expressions are kept and stripped recursively, so an escape hidden in an interpolation is still caught. Short identifier-like literals survive verbatim, because `{"model": x}` and `opts["model"]` are genuine escapes written as strings.
- **Second self-inflicted bug, caught by the existing suite:** blanking *every* literal also blanked `'inherit-launcher'` — the model-neutrality attestation is itself a string, so the first version of the fix rejected every model-neutral script including the guard's own fixtures. Five tests failed immediately. This is the argument for keeping fixtures that exercise the happy path, not just the denials.
- Bound detection moved to the same footing for a stronger reason: the guard reserves what a script *declares*, so a bound in a comment declares nothing. `// HARD_CAP = 9` no longer counts, and a stale commented bound no longer conflicts with the live one.
- Also widened the key pattern — `{"model": x}` was silently missed because the closing quote sits between the word and the colon. A real escape the old lookbehind skipped.
- Known limit, accepted: regex literals aren't tracked (telling `/` division from a regex needs a parser), so a regex containing `model:` still trips the check. Fail-closed and vanishingly rare.

## Self-inflicted incident: a test that wrote to the live config

While fixing a flaky test I wrote `std::env::set_var("HOME", tmp.path())` in a unit test. Being process-global, it leaked to sibling tests, which then wrote into whatever `HOME` pointed at — including, in one run, the real `~/.config/portagenty/`. Verified afterwards that the live config was intact (valid TOML, all 63 workspaces, `default-multiplexer` preserved) and reverted to a read-only fixture.

The lesson is the same one the `EnvSandbox` encodes: **a test may read ambient env, or own a sandboxed copy of it, but must never write the process's env unguarded.** The irony is that the bad fix demonstrated the exact failure mode the good fix prevents.
