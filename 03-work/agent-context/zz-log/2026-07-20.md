## Sol context-window correction

- Corrected `profiles/claude-global/sol-settings.json` from a 150,000-token auto-compaction window to 300,000 tokens. The earlier recovery rail incorrectly treated the proxied route as a 200k window; the opposite correction—advertising the direct API model's full 1.05M—would also be unsafe because `claudex` uses ChatGPT/Codex OAuth rather than direct API access.
- Session forensics confirmed the 150k cap caused the new premature compactions: recent Cynario work compacted repeatedly at approximately 116.7k tokens, matching Claude Code's reserve below that configured window. One session compacted twice within six minutes because post-compaction summaries plus ordinary file reads quickly refilled the small remaining budget.
- The original July 19 overflow evidence was re-measured rather than inferred: KWIR's last successful request carried approximately 345k input tokens before a 153k-character Skill injection; Speakr's carried approximately 372k before the next request. Both then received upstream HTTP 400 context-window errors through CLIProxyAPI. This is consistent with a materially smaller OAuth-route budget than the direct API model's advertised 1.05M window.
- Retained managed auto-compaction at a conservative 300k working window, which triggers around 267k and leaves roughly 100k of observed emergency headroom for large mid-turn tool results. Updated the launcher comment to preserve the API-vs-OAuth distinction.

## Second correction: harness metadata clamp (same day)

- A restarted KWIR session showed `/context` at `x/200k` despite the 300k profile. Cause (verified against Claude Code 2.1.215 docs/issues): the harness treats unknown model ids like `gpt-5.6-sol` as 200k models and **clamps `autoCompactWindow` to that metadata** — the 300k setting was silently `min()`'d to 200k. Fix: `sol-settings.json` now also sets `CLAUDE_CODE_MAX_CONTEXT_TOKENS=300000` and `CLAUDE_CODE_AUTO_COMPACT_WINDOW=300000` via its `env` block (the documented override for gateway-routed foreign models, v2.1.193+). Expected after relaunch: `/context` reads `x/300k`, trigger ~267k.
- Promoted the whole investigation into a durable page: `02-stack/01-ai-coding/context-window-engineering-and-delegation.md` (advertised vs routed vs managed windows; quality/quota/context as joint delegation axes; evidence-labeled route-specific claims). Linked from the 01-ai-coding index; corrected two drifted facts in the CLIProxyAPI page (agent-guard default is 15/prompt + 60/5h, not 40; prevention section now records the standing managed-compaction profile instead of claiming none exists).

## WSL crash root-cause: 3-agent forensics + reclaim

- Bounded wave (3 read-only sonnet agents, disclosed): memory-config audit, disk/VHDX forensics, sync-system inventory. Findings: (1) **crash cause** = `.wslconfig` `memory=24GB` on a **32GB host** — Windows keeps ~8GB and hard-kills the VM under agent load; `autoMemoryReclaim=dropcache` explains the journal's drop_caches churn; (2) **sync system acquitted** — nothing running (Obsidian Headless stale since May 10, OpenClast stopped), though it left 7GiB of duplicated Claude-project pairs on C: and OpenClast's `WATCH_POLLING=true` over DrvFS is a redesign-before-revive hazard; (3) **disk arithmetic** — C: 909GiB used, all VHDXs+pagefile+hiberfil ≈ 183GiB → ~726GiB is Windows-side content (user confirmed: captures, Fortnite ~150GB, provisioning images, installer archive, Downloads). All existing VHDXs are **non-sparse** — `sparseVhd=true` only affects new ones — which is why in-WSL cleanups never returned space to C:.
- In-WSL reclaim executed: rootless-Docker image+build-cache prune (0 active containers) + Playwright/pip/Puppeteer caches → ext4 **86GiB → 51GiB**. Space returns to C: only after the Phase-2 sparse conversion. Held: kwir `target/` (13GiB, full-rebuild cost), 56 Docker volumes (named review needed).
- Windows-side runbook written: `zz-research/2026-07-20-c-drive-reclaim-runbook.md` — SMB triage (robocopy verify-then-delete for Downloads), `wsl --manage --set-sparse`, Docker Desktop/Podman VHDX removal, corrected `.wslconfig` (18GB cap, 4GB swap on D:, reclaim disabled), watchdog-based verification loop.

## Notes / observations

- Workflow and large tool results do consume context quickly, but they were an accelerator rather than the root cause here. The launcher-imposed 150k cap reduced the usable window to ~117k — and even the corrected profile was then silently clamped to 200k by harness metadata until the env override landed.
- Caveat discovered live: `--settings` profiles follow the *session*, not the model. Switching a claudex-launched session to Fable mid-flight keeps the 300k clamp on a native 1M model. Lane changes should be relaunches.
- WSL crash ~15:40 was NOT ck (quarantine held; no ck processes, no OOM-killer records). Signature: abrupt host-side VM kill — corrupted journal, ext4 recovery on reboot, C: at 98% (22 GB free), `hv_balloon` + repeated `drop_caches` pressure, user observed ~20 GB RAM use before shutdown. Host disk pressure + memory ballooning remain the standing suspects; VHDX still ~80 GB after in-WSL sweeps → needs a Windows-side `Optimize-VHD` compact pass.
