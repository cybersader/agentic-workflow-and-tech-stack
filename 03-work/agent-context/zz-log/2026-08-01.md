## Workflow approval lifetime correction

- A real approval attempt arrived after the assistant had spent more than forty minutes composing its response. The pending request's ten-minute timer had started at the blocked tool call, so the nonce was already expired before the human could see and submit it. This disproved the July 31 assumption that requests and grants should share one TTL.
- Changed the lifetime model: a pending request now remains valid for its session and exact target/hash, independent of assistant response latency. Only the one-use grant receives the configured short TTL after the human approves it.
- Strengthened failed-approval recovery. If a nonce is missing, used, or otherwise ungrantable, hook context now forbids manually repeating the rejected line, directs one exact unchanged Workflow reissue to obtain the currently valid guard-emitted command, and forbids silently substituting direct Agent calls or another execution path without human direction.
- Added a deterministic delayed-response regression by aging the recorded request to epoch zero before approval. Also isolated guard tests from the invoking session's model-lock environment; running the suite from a pinned launcher had previously leaked that lock into nominal flexible-lane fixtures.

## Notes / observations

- Human-facing authorization timers should begin when authority is granted, not when an internal request is emitted, unless the user can observe and act on the request immediately.
- Recovery instructions need to constrain both repetition and substitution: preventing a nonce loop is insufficient if the assistant then changes execution strategy without consent.

## Provider-aware proxy launcher preflight

- Traced repeated `503 auth_unavailable` failures to an expired Claude access token whose refresh token was rejected with `invalid_grant`; Codex OAuth remained healthy. The existing `x` flow only ensured that CLIProxyAPI was running, so broken provider auth was discovered by real Claude Code requests and then retried repeatedly.
- Added a non-inference provider checker backed by CLIProxyAPI's loopback Management API plus redacted local credential expiry metadata. It distinguishes login-required authentication failures from transient quota, cooling-down, rate-limit, and upstream states; only authentication failures offer credential replacement.
- Proxy launchers now preflight exactly the providers they route to: pure Sol requires Codex, while mixed Claude/Sol lanes require both Claude and Codex. Native lanes bypass the proxy check.
- The interactive recovery path asks whether to open the short provider login, runs browser OAuth in the foreground, waits for credential hot reload, and continues the original launch arguments automatically. No model probe is sent, preserving the weekly Codex budget.
- Added a private loopback management password, bounded readiness checks, confirmed legacy-proxy restart behavior, short `cliproxy-*-login` helpers, and stubbed tests covering provider mapping, argument preservation, login success/failure/decline/timeout, transient failures, non-TTY behavior, and key permissions.
- Corrected a false-negative found after successful Claude OAuth repair: CLIProxyAPI can retain `status: error` / `context canceled` from an interrupted request while reporting the credential as enabled and available. The auth preflight now treats this narrowly recognized stale cancellation as ready when local expiry is valid; disabled/unavailable credentials still fail closed, and authentication/quota signatures retain their existing classifications.

## Intentional `x` session default

- The first correction replaced native `claude --continue` with an always-fresh default. That avoided stale-index jumps but overcorrected: normal click-through launches unexpectedly lost continuity.
- The final default is index-proof exact-directory continuation. `x` queries pconv's JSONL truth, filters sessions with recorded `cwd == $PWD`, sorts by update time, and resumes the newest exact match via `-r <uuid>`. If pconv/jq is unavailable or no exact match exists, it starts fresh and prints why.
- Native `--continue` remains available explicitly with a stale-index warning, alongside the pconv picker, native `/resume`, fresh launch, and handoff recovery. Regression coverage verifies exact-cwd isolation, newest-match selection, and fail-closed fresh fallback.

## One-run admission for task-specific dynamic Workflows

- Two observed failures shared one cause: the only frictionless Workflow path was a *permanently registered* script, so sessions bent tasks into `bounded-parallel`, guessed at an obsolete saved name, and — when a correctly authored three-phase script was blocked on the locked lane — abandoned the work for something unrelated. Registration is the right gate for a reusable harness and the wrong gate for a graph that exists for one task.
- Added a second admission class. A resolvable `scriptPath` now runs either registered (permanent, hash-pinned) or **one-run approved**: bound to its exact path, sha256, self-declared agent bound, model-neutrality attestation, and the launcher's model lock; one use; never entering the registry. Editing the script, changing its declared bound, or relaunching on a different lane each void a prior approval.
- Locked lanes require a static eligibility check before a nonce is issued: exactly one literal `maxAgents` / `MAX_AGENTS` / `HARD_CAP` bound (conflicting or absent bounds are refused), a literal `subagentModelPolicy: 'inherit-launcher'` line, and no `model:` option, model assignment, computed model key, or nested `workflow()` call. The human must approve at exactly the declared bound — under-reservation and silent capping are both refused, and an over-cap script says so rather than shrinking itself.
- Named Workflows are now consistently denied rather than opaquely approvable: a name cannot be hashed, so its bound and worker model are unattestable. When the name matches a registered id the denial prints that workflow's installed path, so the fix is the same workflow by path rather than a substitution.
- Made the policy file authoritative instead of decorative: `workflowPolicy` must match the guard's implemented rules or the guard refuses to run, and the installer rejects drift before touching HOME.
- Put the taxonomy where it fires deterministically (global + project CLAUDE.md) and the reasoning where it belongs (`context-window-engineering-and-delegation.md` §6). `bounded-parallel`'s own surfaced description now states its single-phase/independent-task scope and forbids standing in for a missing or blocked workflow — with a regression test on that wording, since the description is what a session actually reads.
- Verification: 37 guard tests, 4 installer tests, both JS workflow suites, and a live end-to-end run on the installed guard (block → exact command → wrong count refused → grant → one admitted run reserving all 3 → blocked again), plus live refusal of a model-escaping script and unchanged zero-friction admission of registered `bounded-parallel` on a locked lane.

## Windows/WSL session equivalence in `x`

- The exact-cwd resume shipped earlier today compared raw strings, so the same physical directory recorded as `C:\Users\<you>` (Windows launch) and `/mnt/c/Users/<you>` (WSL launch) looked like two unrelated places. That is why a conversation about moving data to an SMB share was unreachable from `x` at the user root.
- Both pconv queries now share one lexical cwd key: Windows drive paths map onto their `/mnt/<drive>` mount, the drive letter and a trailing separator normalize, and keys are compared for equality. Deliberately no canonicalization (DrvFs stat calls are slow), no symlink resolution, no prefix/descendant matching, and no case folding — a parent, child, other drive, differently-cased path, and the real `/mnt/c/mnt/c/...` tree all still correctly fail to match.
- Regression coverage drives the helper against both spellings in both directions; the previously missing session now resolves from the WSL user root.

## Portagenty literal-path selection

- Traced the find-overlay confusion to two separate facts: typed absolute paths were only fuzzy queries over cached scan results, while the displayed `/mnt/c/mnt/c/...` entries are real empty directories on disk rather than a rendering duplication.
- Updated Portagenty so an existing absolute or `~/` input is pinned first as an `[exact]` candidate and selected on user input. Background scan batches preserve deliberate manual selection, nonexistent paths are not synthesized, and real repeated-prefix directories remain visible rather than being hidden or rewritten.
- Installed the updated local `pa` binary and aligned Portagenty's README, design contract, roadmap, docs concept page, and project instructions. The real `/mnt/c/mnt` tree was inspected but not deleted; cleanup remains a separate destructive action requiring explicit confirmation.
